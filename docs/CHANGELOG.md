# 变更记录

## v1.4.8 · 2026-11-10

### 横屏那一堆问题，根子找到了
- 壳的 `screenOrientation` 从 **13（fullUser）改成 4（sensor）**。
  fullUser 会尊重系统的「自动旋转」开关：把自动旋转关掉的人，手机横过来
  窗口一动不动，界面只能自己 CSS 转 90°，于是「UI 倒了」「视角没转」全来了。
  sensor 直接按重力转，不看用户那个开关；又不像 fullSensor 那样带倒置竖屏，
  手一歪不会整屏翻 180°。
- 界面方向改成**窗口优先**：系统转完窗口，陀螺仪还是旧读数时不再反向转回去
  （之前就是这样叠成 180° 的）。陀螺仪只在「设备转了、窗口没转」的过渡态
  里兜底，而且先等 380ms 看系统转不转。
- 自己转 90° 的方向符号取反：之前横过来整体是倒的。
- 删掉「横竖切换就重开一路摄像头」：那一下要 0.5~1s，就是卡顿的来源。
  现在只重排布局，另外加了一次「横屏拿到竖流」的自动校正（宽高对调重开一次）。
- `videoRot` 一次性迁回 `auto`：老版本为扳正躺倒画面手动设过 90/270 的，
  会跟系统旋转叠成 180°。

### 全屏取景（手动）
- 顶栏新增全屏按钮，右上角有浮动退出按钮；竖屏横屏都适配。
- 非全屏：顶栏 / 工具条 / 快门各占一行，画面吃剩下的全部高度；手机横过来
  窗口自己转，水印自动挪到空着的角落 —— 旋转的意义只是换个水印位置。
- 全屏：顶栏、工具条、快门全部浮层压在画面上，取景吃满整屏。

### 过渡
- 切换横竖屏 / 进出全屏时，取景框尺寸走 260ms 缓动（`.layout-anim` 只挂 460ms，
  平时拖窗口不受影响），不再硬跳。

## v1.4.7 · 2026-11-10

横屏这一块推翻重做：不是排版问题，是壳把窗口钉死在竖屏。

### 横屏为什么一直是错的

壳的 `AndroidManifest.xml` 里 `screenOrientation=1`（portrait），窗口永远不转。
后果是连锁的：

- WebView 报给页面的视口永远是竖的 → 界面只能自己 CSS 转 90°；
- **摄像头也按竖屏出画面** → 横着拿只能得到一条竖版的流，
  取景框无论怎么调都是「中间一条带」，两侧全是空的；
- 自己转 90° 的方向判断还反了 180°，横过来看到的是上下颠倒。

改法是把 Activity 的 `screenOrientation` 改成 **13（fullUser）**：
系统按重力真的转窗口，摄像头给出横版的流，界面不用再假装旋转。
它的 `configChanges` 本来就带着 `orientation|screenSize|smallestScreenSize`，
所以旋转不会重建 Activity，相机不会重启、开屏也不会重放。

CSS 那套自动旋转保留成兜底（系统开了旋转锁、或个别机型窗口转了 WebView 不跟着
resize 时才会走到），并且把转错方向的判断修好了。

### 取景框尽量大

- 横屏：画面铺满整块屏幕，顶栏/工具条/快门都是浮层；
- 竖屏：固定 3:4、`object-fit:cover` 填满；
- 默认视野从「完整」（contain，会在框里留边）改成「填满」，
  并把还停在「完整」的老设置一次性迁过来。

### 图标

启动器图标改成直接渲染 App 自己的 `www/icons/icon.svg`，
和开屏页那个图标是同一张图，桌面、开屏、App 内三处一致。

### 开屏不再闪图标

Android 12+ 的系统开屏页是强制的，躲不掉，但可以把它调成「和开屏动画同底色、
不画图标」：`windowSplashScreenAnimatedIcon` 改成透明色，
`windowSplashScreenBackground` 对齐开屏动画的 `#0b0e14`。
启动过程变成「一块深色底 → 开屏动画淡入」，中间不再跳一下图标。

## v1.4.6 · 2026-11-10

成片分辨率改成可选档位。原先只有「原生满幅 / 跟随预览」两个模糊的概念，
而且「原生满幅」在多数 WebView 里名不副实（见 v1.4.5）。

### 档位

`自动 / 12MP / 8MP / 5MP / 2MP`，统一按 4:3 折算：

| 档位 | 目标尺寸 | 说明 |
|---|---|---|
| 自动 | 设备上限（封顶 3000 高） | 默认，等价于以前的「原生满幅」 |
| 12MP | 4000×3000 | 多数 WebView 拿不到，诊断会标出实际值 |
| 8MP | 3266×2448 | |
| 5MP | 2582×1936 | |
| 2MP | 1633×1225 | 最省时，接近预览档位 |

### 三条设计取舍

**只缩不放。** 源图没有那么多像素时，把它放大到目标尺寸只是把同样的信息
摊到更多格子上，看着更糊，还骗自己「这是 12MP」。这种情况保持原尺寸，
在「相机信息」里写成 `2880x2160（目标 4000x3000）`，一眼就能看出设备上限。

**低于预览档位时不折腾。** 选 2MP 而预览流本身是 1440×1080，再切一次采集
约束只为了多几万像素，要多花 400ms 还可能闪黑，不值。

**换档不重启摄像头。** 分辨率只在按快门时用到，切档位不该打断预览。

### 迁移

旧设置只有 `quality: high|standard`，按 `high → 自动`、`standard → 2MP` 一次性
迁过来（`stillMigrated`），之后用户自己选什么就是什么。

### 诊断

「成片」一行现在会带上目标值；「锐化」一行在超过 8.4MP 跳过时也会如实标注，
不再假装处理过。

验证：新增 `build/_still-check.js` 跑三档实拍 —— 自动 2880×2160、12MP 2880×2160
（目标 4000×3000）、2MP 1440×1080，输出全部不超目标、也没有被放大。

## v1.4.5 · 2026-11-10

对着原生相机比出来的：同一张桌子，我们的成片是「软」的，原生是锐的。
量化一下（两张都统一到 1440×1920，取画面中心区算拉普拉斯方差）：

| | 中心区边缘能量 |
|---|---|
| 原生相机 | 1014 |
| 此刻相机 | 392（**39%**） |

不是分辨率不够（两张像素数相同），是真的没对上焦 + 高频被磨掉了。

### ① 对焦：按下快门那一刻，镜头正在移动

旧流程是 `warmUp(3)` 之后抓 3 帧、间隔 80ms，总共不到 250ms。
`continuous` 对焦模式下镜头一直在来回找，抓到哪一帧看运气 ——
这就是「有时清楚有时糊」。

现在是三步：

1. 先丢一次 `single-shot`，把镜头从「持续搜索」切到「打一次靶」
2. 每 90ms 抓一帧算 ROI 拉普拉斯方差，最多等 700ms；
   分数连续两帧不再上涨就提前收工（AF 收敛通常 150~450ms）
3. 在候选里挑**分数最高**的一帧，不是最后一帧

连拍只保留最优的那张，其余立刻把画布后备存储置零 ——
12MP 一帧占 48MB，五张一起留会直接 OOM。

### ② 分辨率：`takePhoto()` 在 WebView 里是假的满幅

`ImageCapture.takePhoto()` 在多数 Android WebView 上只是把当前视频轨
快照一份，尺寸等于预览流（实测输出 1920×1440，即 2.7MP）。
所以设置里那个「原生满幅」一直是名不副实。

现在先校验：`takePhoto()` 返回的位图若不超过预览流宽度的 1.25 倍，
判定为「假满幅」丢弃，改走真正的办法 —— **临时把采集约束推到最大**
（上限压到 3000 高，再大 WebView 的预览输出一般不支持），抓完立刻恢复。
切换瞬间用静态帧盖住，不会闪黑。

### ③ 锐化：补回被低通掉的高频

预览流到我们手里之前已经过好几轮低通（YUV 转换、纹理缩放、编解码）。
新增非锐化掩模（4 邻域均值当模糊层，中心加权还原），强度 0.52~0.7，
按是否被放大调整。顺序是**影调之后、画水印之前**：

- 放在影调之前：S 曲线会把锐化过冲再放大，暗部边缘出白边
- 放在水印之后：水印文字被一起锐化，笔画发毛

超过 8.4MP 自动跳过 —— 12MP 逐像素跑 JS 要 600ms 以上，
按完快门等太久反而像卡死。

实测同一张样张锐化后边缘能量 +40%，且平坦区与 alpha 完全不变。

### ④ 相机信息里能直接看到瓶颈

新增两行：`对焦`（等待毫秒数 / 连拍帧数）、`锐化`（强度 / 百万像素）。
「取图」一行现在会出现 `hires`，看到它就说明高分辨率那条路走通了；
若仍是 `video`，说明机型不支持更高的预览档位，只能靠对焦和锐化。

测试：tone 20、imgproc 20（新增 5 项锐化）、exif 11、layout 456、e2e 25、修复验证 13，全过。

## v1.4.4 · 2026-11-10

对着原生相机比出来的两个硬差距：**视角窄**、**帧率低**。

### ① 视角：请求竖版尺寸，等于让浏览器裁一刀

v1.4.3 只是去掉了 `aspectRatio`，但请求的仍是**竖版** `810×1080`。
传感器是横的，WebView 手上只有 1440×1080 / 1920×1080 这些整幅档位，
为了交出一个 3:4 的竖框，它会把整幅**中心裁切**后再给你 —— 1440×1080 裁成
810×1080，水平只剩 56%，等效 1.8× 数码变焦；若是 16:9 的流，只剩 42%。

现在改为按 **4:3 横版**要（720→960×720 / 1080→1440×1080 / 1440→1920×1440），
拿到的是整幅，裁不裁由前端决定。

配套两件事：

- 视野默认改成**完整**（`contain`），像原生相机那样两侧不裁
- 水印层不再盖整张卡片，只盖**画面矩形**。之前视野一放宽，水印会飘到画面外的留边上

### ② 帧率：被一句话锁死在 30

`frameRate: { ideal: 30 }`。手机上 120Hz 的屏、能出 60fps 的摄像头，
全被这一句压到 30。

现在自动识别屏幕刷新率（用 rAF 间隔中位数吸附到 30/48/60/90/120 档），
按它请求：屏幕低于 45Hz 就跟随，否则一律要 60。

设置 →「相机信息」里新增一行 `屏幕 / 实际`，例如 `120Hz / 60fps`，
能直接看出瓶颈在摄像头还是渲染。

### ③ 约束级联降级

部分设备（包括浏览器自带假摄像头）不接受「分辨率 + 帧率」的复合约束，
直接抛 `OverconstrainedError`，表现是「没找到可用摄像头」。
现在按 完整约束 → 只留尺寸 → 只要能出画面 三级降级。

## v1.4.3 · 2026-11-10

三个「看起来是界面问题、其实是底层行为」的毛病。

### ① 切后台再回来，取景框里一张巨大的播放按钮

`stopStream()` 会把 `video.srcObject` 置空。元素还在，但已经没有媒体了 ——
Android WebView 此时会画出它**自带的媒体占位图**：一块灰底加一个巨大的
播放箭头。切后台、换前后摄、改预览尺寸都会走这条路径，所以不只是「切屏」。

现在：停流**之前**先把最后一帧抓成 JPEG（连水印一起烤进去），盖在 video 上面，
再把 video 藏起来。回到前台、新流首帧上屏后再撤掉占位。视觉上就是「画面暂停」。
另外加了一段 `::-webkit-media-controls` 规则做双保险，防止某些机型绕过这层。

### ② 相机视角被拉近

`streamConstraint()` 里原本有 `aspectRatio: { ideal: 3/4 }`。浏览器为了满足这个
比例，会把传感器给的 16:9 / 4:3 全幅**中心裁切**后再交给页面 —— 等于凭空加了
一个 1.5~1.8 倍的数码变焦。用户看到的就是「视角怎么这么近」。

去掉 `aspectRatio`，只报尺寸，让 WebView 返回最接近的原生档位，裁切交给前端。

同时新增设置项**视野**：

- 填满（默认）：3:4 取景框，`object-fit: cover`，画面铺满
- 完整：`contain`，不裁两侧，预览与成片都保留全部场景（照片比例随摄像头）

### ③ 不会自动对焦

之前只有点画面才触发一次 `single-shot`，其余时间靠摄像头默认行为，而不少
WebView 默认给的是固定焦点，远景一直糊。

现在开流后按 `focusMode` 能力协商：支持 `continuous` 就设连续对焦并读回校验；
只支持 `single-shot` / `auto` 就每 3 秒补一次；切后台时清掉定时器。

### ④ 启动图标

APK 里只有一个 432px 的方形 PNG，而且它自己是「深色圆角方块 → 半透明描边小方框
→ 相机」三层嵌套。Android 12 的启动画面会把它再套进一个圆底，一屏上看过去是
四个同心容器。

重绘为单层：满幅圆形深色底 + 一枚相机，四角透明。系统无论裁圆还是加底，都只是
给这个圆再包一层，同心不打架。生成脚本 `tools/make_icon.py` 可复现。

## v1.4.2 · 2026-11-10

这一版只做三件事：**别再发白**、**取景框变大**、**手机横过来真的会转**。

### ① 「发白」的两个真凶

**真凶一：EV 被记住了。**

`exposureCompensation`（EV 滑块）之前写进了 localStorage。用户为了「亮一点」
把滑块往右拉过一次，这个 +2.0 就永久留在设置里，之后每次启动都带着两档
过曝去拍 —— 不管场景多亮，出片必白。

EV 是「针对当下场景的临时判断」，不该跨会话记忆。现在：

- 启动一律归零（`readSettings` 里强制 `s.ev = 0`）
- 不再写入 localStorage
- 拉到 ±1.5 以上会提示「偏高，容易发白」

**真凶二：曲线只有「重塑」，没有「归位」。**

旧 `buildLut` 做的是黑场归位 + 伽马锚中位 + S 曲线，但伽马被钳在
`[0.72, 1.38]`。一张中位 0.85 的过曝图想锚到 0.46 需要伽马 4.7，
钳到 1.38 只能压到 0.79 —— 等于没压。曲线再花哨，输入本来就白，输出必然还白。

同时实测发现反向问题：**正常图会被它推爆**。原生相机那张（p95=217、零溢出）
经旧曲线处理后 p95 涨到 249、溢出 4.7% —— 「越修越白」。

现在补上缺的那一环，并收住高光：

| 环节 | 旧 | 新 |
|---|---|---|
| 曝光 | 无（只靠伽马） | 中位 > 0.58 / p95 > 0.90 / 有溢出时，按 `log2(0.47/中位)` 做线性归位（最多 -2 档） |
| 白场 | p99.5 直接当 255 | p99.5 落到 0.94，留 6% 给 S 曲线转弯 |
| 高光 | 软膝渐近 1.0 | 渐近 0.985，**永不触顶** |
| S 曲线 | 0.32 | 0.22（只加一点通透，不再顶爆） |
| 伽马 | 0.72~1.38 | 0.92~1.25（只做微调，不再假装能救过曝） |

实测（同一张样张，离线跑 LUT）：

| | mean | std | p50 | p95 | 溢出 |
|---|---|---|---|---|---|
| 原生相机原片 | 132.7 | 66.5 | 131 | 217 | 0% |
| 旧算法输出 | 137.0 | 86.0 | 133 | **249** | **4.7%** |
| 新算法输出 | 129.6 | 76.5 | 128 | 227 | 0.1% |

人为把样张提亮 1/1.5/2 档模拟过曝后，新算法能把中位从 215/255/255
压回 98 附近、溢出清零。

### ② 取景框不再是一条横带

`layoutStage` 原先按 **视频流比例**算取景框。Android WebView 给的预览流
常见是 16:9 横向（元数据宽 > 高），竖着拿手机时按这个比例排版，
画面上就只剩一条矮横带 —— 用户截图里 393pt 宽的屏幕上只有 320×204。

现在取景比例固定，与流无关：

- 竖屏 **3:4**（与成片比例一致，所见即所得）
- 横屏 **铺满整块**（顶栏、工具条、快门全部改成浮层，不再抢高度）
- `video` 用 `object-fit: cover` 填满，不再留黑边

同一台机器上，取景框从 **320×204 → 369×492**（面积 ×2.7）。

水印缩放基准同步改为**画面短边**（`min(W,H)/1080`）。原先按宽度算，
横屏时画布宽 873 会让字号翻倍，水印直接盖掉半屏。

### ③ 横屏：陀螺仪驱动 + 可锁定

根因在壳里：`AndroidManifest.xml` 的 `screenOrientation=1`（PORTRAIT）把
Activity 钉死在竖屏，系统永远不会转窗口，`window.innerWidth` 永远是竖的。
所以 `@media (orientation:landscape)` 和所有基于它的横屏逻辑在本 App 里
**从来就没生效过** —— 这就是「手机横过来界面不动」。

现在自己实现旋转：

- 读 `deviceorientation` 的 `beta/gamma`，算重力在机身坐标系的方向
  （`gx = -cosβ·sinγ`，`gy = -sinβ`），判断正立 / 倒置 / 左横 / 右横
- 连续 3 帧（≈150ms）同向才切换，避免手抖来回跳
- 横放时给 `#app` 加 `rotate(±90deg)` 并交换宽高，等于自己转了一次屏幕
- 顶栏右侧新增**方向按钮**：点一下锁定当前方向（图标变锁、高亮），
  再点恢复自动。锁定时陀螺仪事件被忽略，画面保持不动
- 没有传感器时（桌面浏览器）退回视口比例判断

转屏会按新方向重新协商一路流（竖屏 3:4 / 横屏 4:3），延迟 480ms 执行，
避免手抖来回转时反复开关摄像头。

### ④ 画面方向兜底

少数机型 WebView 不做 display rotation，画面会横躺 90°。设置里新增
「画面方向」：自动 / 顺时针 90° / 逆时针 90°。选 90° 时预览与成片一起转
（`rotateSource` 先转再裁），不会出现「预览正、成片躺」。

## v1.4.1 · 2026-11-10

这一版解决的是「卡、糊、白、黑屏」四件事。它们的根因只有两个。

### ① 预览流请求了 4.9MP，这是卡/糊/白的共同原因

旧约束是 `width:2560, height:1920`，真机上回的是 **1920×2560**（用户截图里的「预览流」）。
Android WebView 推不动这个尺寸的预览：

- 帧率掉下去 → **卡**
- 帧率低意味着每帧曝光积分时间被拉长 → 运动模糊，**糊**
- 同样场景下更长的积分 → 平均亮度更高，**发白**

原生相机的做法本来就是「预览低分辨率保流畅、拍照走满幅」，现在照做：

- 预览默认长边 **1080**（竖屏 810×1080，横屏 1080×810），并提供 **720P / 1080P / 1440P** 切换
- 成片仍由 `ImageCapture.takePhoto()` 拿原生满幅（实测 3024×4032），不受预览尺寸影响
- 转屏时按新方向重新协商分辨率，横屏不再拿着竖屏的 3:4 流

### ② 每帧都在跑的 CSS 滤镜

预览层原先无条件挂着 `filter: contrast() brightness()`。对一个 1920×2560 的视频层，
每帧都要多跑一遍 GPU 滤镜通道 —— 这是卡顿的第二大来源。

现在只有用户手动拉过「亮度」滑块时才挂滤镜（那时确实需要所见即所得）；
自动影调只作用于成片，预览保持摄像头原始画面。

### ③ 切后台回来卡住 / 拍出全黑

原代码里 **完全没有** `visibilitychange` / `pagehide` 处理。WebView 把页面挂起后，
摄像头轨道被系统掐掉，但 `video.srcObject` 还挂着已经结束的流：

- 画面停在最后一帧或全黑 → 「卡住」
- 按快门抓到的是这张死帧 → 「点了能拍，但照片全黑」

现在：

- 隐藏时主动 `stop tracks` + 解绑 `srcObject`
- 回到前台自动重新开流（`visibilitychange` / `pageshow` 双保险）
- 开机 / 切换 / 转屏 / 唤醒全部走同一把代次锁（`startSeq`），并发启动时新的作废旧的
- 出片前用 48×48 采样算平均亮度，**低于 3.5 判定为死帧**，自动重开摄像头再抓一次；
  仍为黑则明确提示，不再产出黑照片

### ④ 横屏自适应 + 水印自动换角

位置原来只有 `bottom / br / top` 三个特例，其余一律当左下，横屏时没有可用位置。
现在拆成「上/下」×「左/右」的正交维度，共 **左下 / 右下 / 左上 / 右上** 四角。

- 手机横过来，水印自动移到 **右上**，避开左上工具条与底部快门；转回竖屏自动回原位
- 设置里可以关掉这个自动行为（「横屏自动挪到右上」）
- 墨水取样也跟着落点走，取对应那个角的亮度，不再永远取整条横带
- 横屏布局重做：工具条浮到左上（只占 42% 宽），控制条浮到底部，取景器 309×232 → **505×379**

### ⑤ 其它

- 后台不再做每秒一次的签名计算
- 修掉 `initLevel()` 被调用两次的问题

## v1.4.0 · 2026-11-10

这一版是把「发白」真正修掉的一次，同时按反馈做了减法。

### 影调引擎重写（`www/js/tone.js`）

上一版用 `brightness(0.8)` 全局压暗来「压高光」，方向就错了：

> 实测那张照片 P99 从 218 掉到 174，动态范围从 203 **缩到 162**。
> 乘法只是等比压扁，永远不会拉开层次 —— 所以用户反馈「完全没有解决」。

现在改成三段式查找表：

1. **黑场归位**：把 P1 拉回接近 0（只回收 60%，留一点脚避免死黑）；
2. **中位锚定**：用伽马把 P50 送到 0.46，整体明暗不偏；
3. **S 曲线 + 高光软膝**：暗部再压、亮部再抬，knee 以上用指数软压缩，不出断层。

白场锚点也修了一个坑：原来用 P99.5，但那张照片 P99.5=248、P98=144，
说明 248 只是零星反光，拿它当白场会把整幅压在下面，高光永远顶不上去。
现在检测到「长尾分布」时改用 P98 加余量。

实测同一张照片：

| 指标 | 原生 | 处理前 | 处理后 |
|---|---|---|---|
| 标准差 | 67.6 | 41.9 | **69.7** |
| 动态范围 | 214 | 219 | **250** |
| P98 | 223 | 144 | **184** |

### 白平衡改白点法

原来用灰世界，结果把青色笔记本机身当成「蓝色偏」强行拉回中性，
通道偏差从 13 降到 4，数字好看但画面更灰 —— 这正是 Buchsbaum 灰世界假设在单色场景失效的经典case。
现在改用 ≥P95 高光区的通道均值估计光源色，限幅 ±10%，3% 内当噪声不动。
同类场景下增益稳定在 1.00/1.00/1.00，机身颜色得以保留。

### 取图路径：不再把好图换掉

`shouldReplacePhoto` 原规则「溢出比例差 > 6% 就换掉原生图」误伤严重：
屏幕、台灯、白墙在 12MP 原生图上本来就是高光，视频流因为动态范围窄把它压平了，
于是每次都判成「原生图偏亮」，把 12MP 换成了 5MP 的视频帧 —— 画质、视野、色彩全崩。
现在只在原生图过半像素死白（>55%）时才弃用。

### 做减法

- **移除定时拍摄**：反馈「没什么用」；
- **移除九宫格**：与取景、画质无关；
- **移除「多摄探测」**：原来会对每个后置摄像头各开一次流再关掉，4 摄机型要开合 4 次，
  每次几百毫秒且画面闪烁 —— 这是卡顿的主因；
- **移除裁切变焦**：裁切冒充变焦只是把中心放大，视频流本来就 4.9MP，再裁更糊。
  现在只用传感器 zoom 能力，设备不支持就不给变焦入口；
- 水印重绘 500ms → 1000ms，影调采样 1800ms → 2400ms 且关掉自动影调时不再采样。

### 水平仪

旧版只读 `gamma`，那只在竖屏成立；横屏时手机的「左右」对应 `beta`，
所以一转屏就彻底失准。现在按 `screen.orientation.angle` 选轴，
并对角度做一阶低通平滑。视觉上也改了：刻度固定、基准线转动，才看得出差多少。

### 横屏布局

原来横屏时取景器只有 309×232（视口 900×420），原因是底部控制条和工具条各占一段文档流高度。
现在两者在横屏下改为浮层，高度全部还给画面 → **500×375**，提升 65%。

### 相机诊断

设置面板底部新增「相机信息」，直接显示本次拍摄的预览流分辨率、
取图路径（`capture` 原生满幅 / `video` 预览流）、成片尺寸、影调参数。
不用连电脑看 console，截图就能定位问题。

### 文献

新增 `docs/ALGORITHM.md`，18 篇文献逐条对应到实现或说明为何不采用。

## v1.3.3 · 2026-11-10

拍摄算法整体过了一遍，四处改动都能用测试量化。

### 对焦评分（`sharpness` → `frameQuality`）
原来把整帧缩到 320px 再算拉普拉斯方差。320px 这一步本身就是低通滤波，高频细节被抹掉，三帧之间的清晰度差异被压平，择优基本等于抽签。
现在改为：取画面中央 62% 区域（主体基本都在这里）、按最高 640px 采样，再算拉普拉斯方差，同时输出「平均梯度强度」用于识别白墙/天空这类本来就没细节的画面。

### 多帧择优
- 三帧之间插入 80ms 间隔。原来仅隔一个 `requestVideoFrameCallback`，两帧内容几乎一样，抓不到手抖和镜头拉风箱造成的差异。
- 选择不再只看清晰度：过曝的帧即使方差更高（高光边缘会拉高方差）也要压分，`score × (1 - min(0.9, 3 × 溢出比例))`。白掉的细节救不回来，清晰没有意义。

### 渐进降采样
单次 `drawImage` 缩放超过 2 倍时，双线性采样会跳过大片像素，出现锯齿和糊边。现在按 `downscalePlan` 逐级减半（4000 → 2000 → 1000），再做最后一次落到目标尺寸。

### 高光保护（百分位）
`tone.js` 的 `analyze` 现在同时算 50 / 98 / 99.5 百分位亮度。在原有档位建议之外加了一层保护：当溢出比例 ≥6% 且 99.5 百分位已经顶到 0.98 以上时，把最亮那撮像素线性压到 0.95。取两者中更保守的一个。晴天天空约占 5% 高光，不会误伤；偏暗场景需要提亮时跳过保护。

### 测试
- 新增 `tests/test-imgproc.js` 15 项：清晰/模糊对比、纯色零分、过曝帧压分、降采样计划
- `tests/test-tone.js` 扩到 26 项：新增百分位、高光保护、提亮不受压三条边界
